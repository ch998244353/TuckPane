# 3.1.0 更新功能：用户手测

发布状态更新（2026-09-12）：用户已追加授权直接发布 4.0，正式版本号为 4.0.0。下文保留首版更新器的隔离验证步骤和历史候选版本，不能视为这些人工检查已经通过，也不再是本次发布的等待门槛。构建脚本默认复用当前 `artifacts/publish/v4.0.0` 的运行依赖；验证场景仍固定使用测试版本 3.0.9 → 3.1.0。

本轮只验证更新入口、两种发行版的升级和数据保留，不重测旧功能。所有窗口操作、安装和重启由用户执行；交付脚本只构建文件。

## 1. 测试包与正式候选的区别

正式候选是 `3.1.0`，连接真实 GitHub 正式 Release。线上 `3.0.2` 没有更新器，因此另提供含同一更新流程的 `3.0.9 → 3.1.0` 验证包，才能在正式发布之前完成实际升级手测。

验证包采用独立编译开关和固定本地 `update-feed`，不依赖联网或提前发 Release；正式候选没有这个替换入口。验证安装器使用独立 AppId，不创建生产快捷方式、文件关联或右键菜单。验证进程使用独立数据根，不修改生产启动项。安装器会产生自己的卸载记录；缺少 WebView2 时仍可能安装共享的微软运行库。

验证包不是正式发布包，不能上传 GitHub，也不能替换日常使用的版本。验证通过说明升级流程已实际运行，不等于正式候选的字节内容已完成同样的在线升级。

## 2. 开始测试

构建完成后会给出 `artifacts/update-validation/日期-唯一编号` 的具体路径。每次构建使用新目录，不覆盖以前的测试数据。保留目录原有位置，依次测试两种模式。

1. 双击该目录内 `start-portable.cmd`，打开“设置 → 更新”，确认显示 **3.0.9、便携版**，手动检查后显示 **3.1.0**。
2. 在验证程序中建立一个测试收纳窗，仅放入临时文本文件；写一条测试便签和待办，改一个设置并移动窗口。不要选择真实工作目录。程序目录还预置了 `user-extra.txt`，用于核对未知额外文件保留。
3. 点击“更新并重启”。预期正常保存、退出，原便携目录更新为 3.1.0 并重启；核对刚才的设置、窗口、临时文件、便签、待办以及 `user-extra.txt` 保留。若便签或待办窗口未自动打开，重新打开测试文件核对正文。更新页应显示配置备份位置与上次更新结果。
4. 退出便携验证程序，再双击 `start-installed.cmd`。它首次会静默安装 **3.0.9** 到本测试目录内的 `installed-app`，然后带隔离数据根启动；再次运行只启动当前已安装版本。确认更新页显示 **安装版**，重复第 2、3 步，核对升级后仍在原 `installed-app` 目录。不要直接运行 `setups` 里的安装器或程序 exe，以免遗漏隔离环境变量。

两种模式的数据分别在 `data/portable`、`data/installed`，没有复制生产数据。真实状态位于各自的 `LocalAppData/TuckPane`；测试收纳目录位于各自的 `UserProfile/TuckPane`。进程重启会继续使用相同隔离根。

配置备份保存 `state.json`（包括设置、窗口位置和目录关联）以及已有的 `state.json.bak`。注册表中的菜单偏好原位保留，不包含在这个状态文件备份中；真实收纳文件及便签、待办正文也原位保留，不做全量复制。

## 3. 两个短失败检查

在点击更新前进行，任一模式各检查一次即可：

- 将该模式 `data/<模式>/update-feed/release.json` 暂时改名，点击手动检查；预期显示失败而程序仍可操作，改回后能重试。这验证本地供给失败处理，不代表已经测过真实网络断开或 GitHub 限流。
- 开始下载后，如能及时点击“取消”，预期停止下载、保持 3.0.9 可用。由于本地文件读取较快，可能来不及取消；此时记录“人工未覆盖”，复用专项自动测试证据，不重复制造大量尝试。随后重新更新。

## 4. 失败时保留什么

不要删除测试目录或反复覆盖安装。保留各模式 `LocalAppData/TuckPane/updates/result.json`、`sessions` 中的 `installer.log` / `program-backup`，以及 `config-backups`。初次安装失败另看测试目录根的 `initial-install.log`。

若更新后没有自动打开，先使用同一 `start-*.cmd` 启动，再查看更新页；若提示需要重启 Windows，先重启后再启动。若无法启动，提供错误文字、该测试目录和失败步骤即可，不手工把配置或程序备份覆盖到生产目录。便携替换失败会尝试恢复旧程序文件；安装器失败不保证完整自动回滚。

## 5. 反馈与发布门槛

两种隔离升级通过后，再检查正式候选：先从托盘正常退出日常使用的 TuckPane，手动安装交付的 `candidate-3.1.0` 安装包，然后打开“设置 → 更新”，确认 3.1.0、现有窗口/目录/文档保留，以及真实 GitHub 检查可以完成。此时线上还是 3.0.2，显示没有更高正式版是正常结果；不用反复尝试升级。这个步骤使用日常数据，避免与隔离验证程序同时运行或混用安装目录。

请反馈：便携版升级是否通过、安装版升级是否通过、上述代表性数据是否保留、正式候选检查是否通过，以及是否有错误。只完成部分检查不算全通过。用户已于2026-09-12追加授权直接发布4.0.0，因此本清单用于后续人工验收，不再阻塞本次发布。

构建者使用 PowerShell 7，在生产候选构建完成且没有其他构建正在运行时执行一次：

```powershell
pwsh -NoProfile -File .\scripts\build-update-validation.ps1
```

脚本为两个不同版本各发布一次，再各打包一次安装器；不会执行程序、安装器或 GUI 测试，也不会清理已有测试目录。
